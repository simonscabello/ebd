## Ajustes depois da revisão do Codex (revisão adversarial 2)

O Codex CLI revisou o diff do lote 1 (`codex exec --sandbox read-only`, sem acesso ao `.env`). Ele aprovou L2, L3, L4, L6 (comparou 1.702 entradas entre o mapa novo e a varredura antiga: nenhuma divergência), L7, L9 e L10. Apontou três problemas reais, todos corrigidos:

| Problema apontado                                                                                                                                                                                               | Correção                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L1: o `catch (Throwable)` cobria também falhas _depois_ de algum envio, e o fallback reenviaria avisos já entregues. O Codex reproduziu: 201 no primeiro aparelho, exceção no segundo, os dois recebem de novo. | `flush()` só devolve `null` (vai para o fallback) quando a falha acontece no primeiro passo do gerador, que cifra o lote antes de qualquer requisição. Depois que algo saiu, o erro sobe como antes. Novo teste: `WebPushSenderTest::test_a_failure_after_something_was_sent_is_not_retried`.                           |
| L5: o prazo do lock (130 s) podia ser menor que a operação (2 × 60 s + pausa + contexto).                                                                                                                       | Prazo `(timeout + 10) × 2 + 120` = 260 s. O lock é solto no `finally`, então o prazo só vale se o processo morrer. Documentado que o lock exige cache compartilhado entre processos (`redis` ou `database`; `config/cache.php` usa `database` como padrão e o `.env.example` usa `redis`). Com `array` ele não protege. |
| L8: um `CREATE INDEX CONCURRENTLY` interrompido deixa o índice `INVALID`, e `IF NOT EXISTS` o aceitaria calado.                                                                                                 | A migration confere `pg_index.indisvalid` e recria o índice quando ele está inválido.                                                                                                                                                                                                                                   |
